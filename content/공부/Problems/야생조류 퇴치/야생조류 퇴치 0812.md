# WCD Server 현재 실행·구현 상태 정리

## 1. 현재 실행 상태

### PostgreSQL

정상 실행 중입니다.

- 서비스: `active`
- 부팅 자동 실행: `enabled`
- 포트:
  - `127.0.0.1:5432`
  - `0.0.0.0:6000`
- 사용 DB: `agent_dev`
- Timezone: `Asia/Seoul`
- Alembic: `20260805_0002 (head)`

### WCD Server

`tmux wcd-server` 세션에서 실행 중입니다.

- 프로세스: `uvicorn`
- 주소: `0.0.0.0:8888`
- Health: 정상
- DB 연결: 정상

현재 실제 API:

```http
GET  /health
POST /api/v1/episodes
GET  /api/v1/episodes
GET  /api/v1/episodes/{episode_id}
POST /api/v1/episodes/{episode_id}/artifacts
```

`API_REQUIREMENTS.md`에 정의된 영상 스트리밍·검수 API는 아직 구현되어 있지 않습니다.

## 2. 현재 DB 상태

| 테이블 | 데이터 |
|---|---:|
| `alembic_version` | 1 |
| `devices` | 2 |
| `zones` | 0 |
| `device_zone_assignments` | 0 |
| `episodes` | 0 |
| `episode_steps` | 0 |
| `media_artifacts` | 0 |

등록 장치:

- `WCD-01`
- `WCD-02`

### 즉시 확인된 문제

장치는 등록되어 있지만 `zones`가 비어 있습니다.

현재 Episode 저장 시 다음을 검사합니다.

```text
device_id가 devices에 존재
zone이 zones에 존재
```

따라서 현재 상태에서 `WCD-01` 또는 `WCD-02`로 Episode를 요청하더라도, 유효한 zone이 없어 `zone_not_found`로 `422`가 반환됩니다.

또한 `device_zone_assignments` 테이블은 존재하지만 현재 Episode 저장 검증에는 사용되지 않습니다.

즉, 현재는:

```text
device 존재 여부 → 검증함
zone 존재 여부   → 검증함
device-zone 배정 → 검증하지 않음
```

## 3. 파일 저장소 상태

현재 설정된 경로가 둘 다 존재하지 않습니다.

```text
로컬: /var/lib/wcd/videos
NAS:   /mnt/wcd-nas/videos
```

현재 상태:

```text
/var/lib/wcd/videos    → 없음
/mnt/wcd-nas/videos    → 없음
```

따라서:

- Episode metadata 저장·조회는 가능
- MP4 업로드는 저장소 오류로 실패할 가능성이 높음
- NAS archive 불가
- 영상 스트리밍 API를 추가해도 실제 파일을 읽을 수 없음

즉, **DB와 API 프로세스는 정상이나 영상 처리 환경은 아직 준비되지 않은 상태입니다.**

## 4. 현재 가능한 처리

### 가능한 것

구역을 먼저 등록한다는 조건에서 다음 흐름은 가능합니다.

```text
POST Episode metadata
→ episodes 저장
→ episode_steps 저장
→ VIDEO_PENDING

GET Episode 목록

→ DB 조회
```

### 현재 불가능하거나 미완성인 것

```text
MP4 저장             → 저장 경로 없음
브라우저 영상 재생   → 스트리밍 API 없음
영상 구간 탐색       → Range API 없음
검수 저장            → 테이블/API 없음
검수 조회            → 테이블/API 없음
Agent 판정 전달      → connector 없음
Agent 결과 반영      → projection API/테이블 없음
Q-table 관리         → 테이블/API 없음
장치 인증            → 없음
```

# 5. 우선순위별 업데이트 항목

## P0 — 기본 동작 가능 상태 만들기

### 5.1. 구역 기준 데이터 등록

최소한 실제 사용할 구역이 필요합니다.

예:

```text
A
B
```

필요하다면 장치 배정도 등록합니다.

```text
WCD-01 → A
WCD-02 → B
```

다만 `device_zone_assignments`를 실제 Episode 저장 검증에 사용할 것인지 먼저 결정해야 합니다.

권장 정책:

```text
Episode 수신 시각에
device-zone assignment가 유효해야
Episode 저장을 허용한다.
```

이 정책을 적용하려면 repository의 Episode 저장 검증 로직도 함께 변경해야 합니다.

---

### 5.2. 로컬 영상 저장소 준비

필요 경로:

```text
/var/lib/wcd/videos
```

필요 작업:

- 디렉터리 생성
- `uvicorn` 실행 사용자에게 쓰기 권한 부여
- 충분한 디스크 용량 확인
- `systemd`/`tmux` 실행 사용자의 권한 일치
- 실제 upload 후 MP4 파일 저장 검증

---

### 5.3. NAS 연결 정책 결정

현재 예정 경로:

```text
/mnt/wcd-nas/videos
```

다음 사항을 확정해야 합니다.

- 실제 mount point
- NFS / CIFS 방식
- mount source
- 파일시스템 타입
- sentinel 파일
- 서버 재부팅 후 자동 mount
- NAS 장애 시에도 로컬 업로드를 계속 받을지 여부

# 6. P0 — 대시보드 요구 API

## 6.1. 영상 스트리밍 API

신규 구현이 필요합니다.

```http
HEAD /api/v1/artifacts/{artifact_id}/media
GET  /api/v1/artifacts/{artifact_id}/media
```

필수 기능:

- `200`
- `206 Partial Content`
- `416 Range Not Satisfiable`
- single byte range
- `Content-Length`
- `Content-Range`
- `Accept-Ranges: bytes`
- ETag에 SHA-256 사용
- `Content-Disposition: inline`
- 파일 전체를 메모리에 올리지 않는 streaming
- Local / NAS 파일 선택
- path traversal 차단
- symlink 탈출 차단
- DB metadata와 실제 파일 크기 검증

---

## 6.2. Episode 상세에 재생 정보 추가

권장 응답:

```json
{
  "playable_artifact": {
    "artifact_id": "...",
    "filename": "episode.mp4",
    "size_bytes": 123456,
    "sha256": "...",
    "mime_type": "video/mp4",
    "etag": "...",
    "media_url": "/api/v1/artifacts/.../media"
  }
}
```

기존 `artifact_refs`는 유지하고, 서버가 실제 재생 가능한 대표 영상을 별도로 선택하는 구조가 좋습니다.

즉:

```text
artifact_refs
→ Episode와 연결된 전체 artifact

playable_artifact
→ 대시보드에서 즉시 재생할 대표 영상
```

## 7.1. 검수 DB Migration

최소 `episode_reviews` 테이블이 필요합니다.

주요 컬럼:

```text

```

근거 artifact는 별도 연결 테이블을 권장합니다.

```text

```

---

## 7.2. 검수 API

필요 API:

```http
GET /api/v1/episodes/{episode_id}/review
PUT /api/v1/episodes/{episode_id}/review
```

필수 동작:

- 기록 없음 → `200 null`
- 최초 `PUT` → `revision 0`
- 성공 후 → `revision 1`
- 조건부 `UPDATE`를 통한 optimistic locking
- 오래된 revision 요청 → `409`
- Episode 존재 여부 확인
- evidence artifact가 동일 Episode 소속인지 확인
- 상태별 필수값 검증

권장 revision 흐름:

```text
Client GET
→ state_revision = 3

Client PUT
→ expected_revision = 3

DB UPDATE
WHERE state_revision = 3

성공
→ state_revision = 4

이미 다른 사용자가 수정함
→ UPDATE 0 rows
→ 409 Conflict
```

# 8. 검수 계약에서 먼저 수정할 부분

`API_REQUIREMENTS.md`를 그대로 구현하면 Agent 계약과 다시 충돌합니다.

## 8.1. 명칭 통일

권장:

```text
exited_at   → exit_at
returned_at → reentered_at
workflow    → review_status
```

---

## 8.2. outcome 재정의

현재 대시보드 정의:

```text
EXIT
MOVE_AWAY
NO_RESPONSE
FEEDING_CONTINUED
OCCLUDED
```

Agent 정의:

```text
SUSTAINED_DETERRENCE
TEMPORARY_DETERRENCE
PARTIAL_RESPONSE
NO_RESPONSE
FEEDING_CONTINUED
```

`OCCLUDED`는 행동 결과라기보다 **학습 제외 사유**에 해당합니다.

권장 계약:

```text
outcome:

SUSTAINED_DETERRENCE
TEMPORARY_DETERRENCE
PARTIAL_RESPONSE
NO_RESPONSE
FEEDING_CONTINUED
```

학습 제외 사유는 별도로 관리합니다.

```text
excluded_reason_code:

OCCLUDED
SAFETY_BLOCKED
DEVICE_ERROR
VIDEO_CORRUPT
OBSERVATION_DATA_GAP
```

---

## 8.3. evidence 참조 방식

현재 문서:

```json
{
  "evidence_refs": [
    "artifact://sha256/..."
  ]
}
```

대신 WCD DB의 권위 식별자를 사용하는 것이 좋습니다.

```json
{
  "evidence_artifact_ids": [
    "artifact-video-001"
  ]
}
```

이렇게 해야 서버가 다음을 직접 검증할 수 있습니다.

```text
artifact 존재 여부
artifact의 Episode 소속 여부
artifact의 유형
artifact의 실제 파일 존재 여부
```

## 8.4. point evidence

현재 단일 객체보다 배열이 안전하며, 각 evidence에 `artifact_id`가 필요합니다.

권장:

```json
{
  "point_evidence": [
    {
      "artifact_id": "artifact-video-001",
      "coordinate_schema": "normalized_xy",
      "timebase": "media_time_ms",
      "x": 0.42,
      "y": 0.31,
      "captured_at_ms": 3000
    }
  ]
}
```

이 구조라면 하나의 Episode에서도 여러 영상·시점의 근거를 저장할 수 있습니다.

# 9. Agent 연계를 위한 Episode 계약 업데이트

이전 검토에서 확인한 Agent 요구 필드는 여전히 필요합니다.

`episode_steps`에 추가:

```text
source_sequence
partial_response
reentered_at
occluded
safety_blocked
device_error
video_corrupt
observation_data_gap
```

기존 필드 변경:

```text
time_since_same_action

기존:
float / null

변경:
integer seconds
기본값 0
```

반드시 함께 결정해야 할 사항:

- 신규 계약을 `episode-v2`로 만들 것
- `source_sequence`는 Episode 전체에서 `0`부터 연속 증가
- 품질 플래그는 임의 `False` 기본값이 아니라 실제 Jetson 입력을 필수로 할 것
- `video_corrupted` / `video_corrupt` 명칭 통일
- `reentered_at = null`이 "재진입 없음"인지 "관찰 미완료"인지 구분
- 15분 재진입 관찰 완료 시점 정의
- 기존 `episode-v1` 데이터를 Agent 학습에서 제외할지 결정

# 10. 보안 업데이트

현재 WCD Server는:

```text
0.0.0.0:8888
```

로 열려 있지만 애플리케이션 수준 인증이 없습니다.

현 상태에서는 등록된 장치 ID만 알면 누구든 장치를 가장할 수 있습니다.

예:

```json
{
  "device_id": "WCD-01"
}
```

`device_id`가 DB에 등록되어 있다는 사실은 FK 무결성만 보장할 뿐, 요청자가 실제 해당 장치라는 사실은 증명하지 않습니다.

필요 항목:

- TLS
- 장치별 credential
- HMAC 또는 mTLS
- timestamp
- nonce
- body digest
- replay 방지
- 대시보드 사용자 인증
- 영상 조회 권한
- 검수 수정 권한

권장 요청 인증 구성 예:

```text
device_id
timestamp
nonce
body_digest
signature
```

서버는 다음을 검증합니다.

```text
1. device_id 존재
2. timestamp 허용 범위
3. nonce 재사용 여부
4. body digest 일치
5. signature 일치
```

# 11. 운영 구조 업데이트

현재:

```text
PostgreSQL → systemd
WCD Server → tmux
```

PostgreSQL은 운영 서비스 형태로 관리되고 있지만 WCD Server는 개발용 실행 방식에 가깝습니다.

운영용으로 다음이 필요합니다.

```text
wcd-server.service
```

필수 설정:

- 환경 파일 경로
- 실행 사용자
- 로컬 저장 경로 권한
- NAS 경로 권한
- restart policy
- PostgreSQL dependency
- NAS dependency 또는 mount readiness 처리
- readiness check
- 로그 보관
- log rotation

`tmux`는 개발 중 상시 실행에는 충분하지만 다음 상황을 자동 처리하지 못합니다.

```text
서버 재부팅
프로세스 crash
uvicorn 비정상 종료
dependency startup ordering
자동 restart
```

# 14. 핵심 판단

현재 상태를 한 줄로 정리하면 다음과 같습니다.

```text
DB와 기본 Episode API는 살아 있지만,
실제 운영 흐름은 Zone 기준 데이터와 영상 저장소 단계에서 막혀 있다.
```

가장 먼저 해결해야 하는 것은 새 기능 추가보다 **기본 end-to-end 경로를 실제로 한 번 통과시키는 것**입니다.

우선:

```text
Zone 등록
→ Device-Zone 정책 적용
→ 로컬 영상 경로 준비
→ 실제 Episode 생성
→ MP4 artifact 저장
→ Episode 상세 조회
```

까지 성공시키는 것이 좋습니다.

그 다음에:

```text
영상 스트리밍
→ 검수
→ Episode v2
→ Agent 연계
→ 인증 / 운영 고정
```

순서로 확장하는 것이 안전합니다.
