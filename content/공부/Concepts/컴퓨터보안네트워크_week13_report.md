## 1. Security of LLM-based Agents Regarding Attacks, Defenses, and Applications: A Comprehensive Survey



### 개요

이 논문은 LLM 기반 에이전트의 보안 문제를 공격, 방어, 활용이라는 세 관점에서 종합적으로 정리한 서베이 논문이다.  
LLM 기반 에이전트는 단순히 질문에 답하는 모델이 아니라, 외부 도구 호출, 장기 계획, 환경 인식, 다단계 작업 실행을 수행하는 자율 또는 반자율 시스템이다. 논문은 이러한 에이전트 구조가 기존 LLM보다 훨씬 넓은 공격 표면을 가진다고 본다. ScienceDirect 초록에서도 LLM 기반 에이전트가 외부 도구와 환경을 사용해 복잡한 작업을 수행하면서 단일 LLM 추론보다 공격 표면이 크게 확장된다고 설명한다.

이 논문은 LLM 에이전트에 대한 공격과 방어를 분류하고, 공격 및 방어 기법을 평가하기 위한 기준을 제시한다. 또한 LLM 에이전트가 사이버 공격을 자동화하는 데 사용될 수 있는 동시에, 위협 탐지나 방어 자동화에도 사용될 수 있다는 이중적 성격을 다룬다.

### 핵심 내용

LLM 기반 에이전트는 프롬프트 해석, 메모리, 도구 호출, 계획 수립, 실행이라는 여러 단계를 거쳐 동작한다. 이 때문에 공격자는 단순히 사용자 입력만 조작하는 것이 아니라, 외부 문서, API 응답, 도구 결과, 메모리, 에이전트 간 통신까지 공격할 수 있다.

논문은 LLM 에이전트에 대한 대표적인 공격으로 프롬프트 인젝션, jailbreak, unsafe tool use, memory poisoning, reasoning failure 등을 다룬다. 특히 LLM 에이전트가 외부 도구를 실행할 수 있기 때문에 공격 결과가 잘못된 답변 생성에 그치지 않고 실제 작업 실행, 데이터 유출, 권한 오남용으로 이어질 수 있다는 점을 강조한다.

방어 측면에서는 입력 필터링, 프롬프트 분리, 도구 사용 제한, 메모리 검증, 샌드박싱, 출력 검증, 인간 승인 절차, 다층 방어 구조가 필요하다고 본다. 논문은 공격과 방어 기법을 단순히 나열하지 않고, 각각의 성능을 평가하기 위한 기준을 제시한다는 점에서 일반적인 서베이보다 체계적이다.

### 논문의 주장

저자들의 핵심 주장은 LLM 기반 에이전트 보안은 단순한 모델 보안 문제가 아니라 시스템 보안 문제라는 것이다.

LLM 에이전트는 자연어 입력을 해석하고 외부 도구를 실행하는 구조이기 때문에, 모델 내부의 안전성만으로는 전체 시스템의 안전성을 보장할 수 없다.  
공격자는 모델 입력뿐 아니라 도구 인터페이스, 메모리, 외부 환경, 에이전트 간 통신까지 공격할 수 있다.  
따라서 방어는 입력 필터링이나 모델 튜닝만으로 끝나서는 안 되며, 에이전트의 각 구성 요소를 기준으로 다층적으로 설계되어야 한다.  
또한 LLM 에이전트는 공격 대상이면서 동시에 사이버 방어 도구가 될 수 있으므로, 공격과 방어 양쪽에서 모두 중요한 연구 대상이다.

### 의의

이 논문의 의의는 LLM 에이전트 보안을 공격, 방어, 사이버보안 활용까지 하나의 구조 안에서 정리했다는 점에 있다. 기존 LLM 보안 논의는 프롬프트 인젝션이나 jailbreak처럼 모델 입력 중심의 공격에 집중하는 경우가 많았다. 그러나 이 논문은 LLM 에이전트가 실제 환경에서 도구, API, 메모리, 브라우저, 다중 에이전트 시스템과 연결될 때 발생하는 보안 문제를 더 넓게 다룬다.

특히 이 논문은 LLM 에이전트를 사이버보안에서 양면적인 존재로 본다. LLM 에이전트는 공격자에게 자동화된 공격 도구가 될 수 있지만, 동시에 방어자에게는 위협 탐지, 사고 대응, 보안 분석 자동화 도구가 될 수 있다. 이 관점은 LLM 기술을 무조건 위험한 대상으로만 보거나 무조건 유용한 도구로만 보는 단순한 접근을 피하게 만든다.

### 느낀점

이 논문은 LLM 기반 에이전트를 실제 서비스에 적용할 때 가장 먼저 고려해야 할 보안 관점을 제시한다. 중요한 점은 LLM의 답변이 틀릴 수 있다는 문제가 아니라, LLM이 틀린 판단을 바탕으로 실제 도구를 실행할 수 있다는 점이다.

따라서 LLM 에이전트 보안의 핵심은 “모델이 나쁜 명령을 거절하는가”가 아니라 “모델이 신뢰할 수 없는 입력을 받았을 때 어떤 권한까지 행사할 수 있는가”이다. 에이전트의 권한, 도구 접근 범위, 실행 전 검증, 민감 작업 승인 절차가 함께 설계되어야 한다. 이 논문은 LLM 에이전트를 단순한 AI 모델이 아니라 하나의 실행 시스템으로 보아야 한다는 점을 분명히 보여준다.

## 2. Large Language Models in Cybersecurity: A Survey of Applications, Vulnerabilities, and Defense Techniques

### 개요

이 논문은 LLM이 사이버보안 분야에서 어떻게 활용되고 있으며, 동시에 어떤 취약점을 가지는지 정리한 서베이 논문이다. MDPI에 게재된 이 논문은 LLM의 사이버보안 활용을 위협 탐지, 취약점 평가, 사고 대응, IoT 보안, 블록체인 보안, 하드웨어 보안 등 여러 영역으로 나누어 설명한다. 논문 초록은 LLM이 고급 언어 이해와 문맥 추론 능력을 바탕으로 사이버보안에서 지능적이고 자동화된 접근을 가능하게 한다고 설명한다.

동시에 이 논문은 LLM 자체가 공격 대상이 될 수 있음을 강조한다. 즉, LLM은 보안 방어를 강화하는 도구이지만, 프롬프트 인젝션, jailbreak, 데이터 유출, 편향, 적대적 공격, 모델 오용 등의 취약점도 가지고 있다.

### 핵심 내용

논문은 LLM의 사이버보안 활용을 크게 두 축으로 정리한다. 첫째는 LLM을 보안 업무에 활용하는 방향이다. 둘째는 LLM 자체의 취약점과 이를 완화하기 위한 방어 기술이다. MDPI 초록에서도 이 논문이 LLM을 주요 사이버보안 영역에 통합하는 문제와 LLM 자체의 취약점 및 완화 전략을 함께 다룬다고 설명한다.

LLM은 보안 로그 분석, 위협 인텔리전스 요약, 악성코드 분석, 취약점 탐지, 보안 정책 생성, 침해 사고 대응, 피싱 탐지 등에 활용될 수 있다. 특히 많은 보안 데이터가 자연어 보고서, 로그, 알림, 코드, 문서 형태로 존재하기 때문에 LLM의 언어 처리 능력은 보안 업무 자동화에 적합하다.

그러나 LLM은 보안 분야에서 사용될 때 새로운 위험도 만든다. 공격자가 LLM을 이용해 피싱 이메일을 자동 생성하거나, 악성코드 분석을 우회하거나, 취약점 탐색을 자동화할 수 있다. 또한 방어자가 사용하는 LLM 시스템 자체가 프롬프트 인젝션, jailbreak, 데이터 오염, 민감정보 노출에 취약할 수 있다.

### 논문의 주장

저자들의 핵심 주장은 LLM이 사이버보안의 효율성과 자동화를 크게 높일 수 있지만, 그 자체가 새로운 공격 표면이 된다는 것이다.

LLM은 방대한 보안 데이터를 해석하고, 보안 전문가의 반복 작업을 줄이며, 위협 탐지와 대응 속도를 높일 수 있다.  
그러나 LLM이 생성한 결과는 항상 검증되어야 하며, 보안 의사결정에 그대로 사용되어서는 안 된다.  
LLM 기반 보안 시스템은 프롬프트 공격, 데이터 유출, 모델 오용, 설명 가능성 부족, 신뢰성 부족 문제를 함께 가진다.  
따라서 LLM을 사이버보안에 도입할 때는 성능뿐 아니라 안전성, 검증 가능성, 운영 통제, 방어 전략이 함께 고려되어야 한다.

### 의의

이 논문의 의의는 LLM을 사이버보안의 도구이자 위험 요소로 동시에 분석한다는 점에 있다. 보안 분야에서 LLM은 단순한 챗봇이 아니라, 보안 이벤트를 분석하고 위협을 분류하며 대응 방안을 제안하는 지능형 보조 시스템으로 사용될 수 있다.

하지만 LLM이 보안 업무에 깊이 들어갈수록 잘못된 판단의 비용도 커진다. 예를 들어 LLM이 경보를 잘못 분류하면 실제 공격을 놓칠 수 있고, 잘못된 대응 절차를 제안하면 사고 피해가 커질 수 있다. 또한 공격자가 LLM을 이용해 더 정교한 공격을 자동화할 가능성도 존재한다.

따라서 이 논문은 LLM을 보안에 적용할 때 단순한 성능 향상만 보지 말고, 신뢰성, 검증, 통제, 책임성까지 함께 고려해야 한다는 기준을 제공한다.

### 느낀점

이 논문은 LLM이 사이버보안 분야에서 매우 유용한 도구가 될 수 있지만, 이를 무비판적으로 도입하면 오히려 새로운 위험을 만들 수 있음을 보여준다. 보안 업무는 정확성과 책임성이 중요한 영역이기 때문에, LLM의 답변을 그대로 신뢰하는 방식은 위험하다.

특히 LLM은 보안 전문가를 대체하는 도구라기보다, 반복적인 분석과 문서화, 경보 요약, 초기 분류를 보조하는 도구로 보는 것이 적절하다. 최종 판단은 검증 가능한 로그, 정책, 규칙, 전문가 검토와 결합되어야 한다. 이 논문은 LLM 기반 보안 시스템을 설계할 때 자동화의 효율성과 보안 통제의 균형이 중요하다는 점을 잘 보여준다.

## 3. In-Browser LLM-Guided Fuzzing for Real-Time Prompt Injection Testing in Agentic AI Browsers

### 개요

이 논문은 agentic AI browser, 즉 LLM 기반 브라우저 에이전트가 웹페이지 안에 숨겨진 악성 명령에 얼마나 취약한지를 실시간으로 테스트하는 방법을 제안한 연구이다. 논문은 브라우저 안에서 직접 동작하는 LLM-guided fuzzing 프레임워크를 제시한다. arXiv 초록에 따르면 이 프레임워크는 악성 웹 콘텐츠를 생성하고, 브라우저 내 AI 에이전트에게 입력한 뒤, 에이전트가 숨겨진 명령을 따르는지 관찰하여 새로운 공격을 진화시킨다.

이 논문이 다루는 핵심 문제는 간접 프롬프트 인젝션이다. 공격자는 웹페이지 안에 사용자가 보지 못하는 악성 지시를 숨기고, AI 브라우저 에이전트가 페이지를 요약하거나 질문에 답하는 과정에서 그 지시를 따르게 만들 수 있다.

### 핵심 내용

논문은 기존의 정적 테스트 방식만으로는 AI 브라우저 에이전트의 프롬프트 인젝션 취약점을 충분히 찾기 어렵다고 본다. 따라서 실제 브라우저 환경에서 DOM 구조와 에이전트 행동을 직접 관찰하면서 공격을 반복적으로 생성하는 fuzzing 방식을 제안한다.

이 프레임워크는 두 가지 방식으로 공격 입력을 만든다. 하나는 미리 준비된 프롬프트 인젝션 템플릿을 사용하는 방식이고, 다른 하나는 LLM을 이용해 공격 문구를 변형하고 진화시키는 방식이다. 이후 브라우저 에이전트가 해당 웹페이지를 읽고 어떤 행동을 하는지 관찰한다.

논문은 실제 브라우저 환경에서 테스트하기 때문에 에이전트가 페이지 콘텐츠를 어떻게 읽고, 어떤 DOM 맥락에서 판단하며, 어떤 행동을 실행하는지 더 정확히 관찰할 수 있다고 주장한다. 또한 실험에서 단순한 공격은 대부분 차단되지만, 반복적인 fuzzing을 통해 공격 문구가 정교해질수록 우회 성공률이 높아지는 현상을 보고한다. 논문 초록은 10번째 fuzzing 반복 시점에서 가장 성능이 좋은 도구도 58~74%의 실패율을 보였다고 설명한다.

### 논문의 주장

저자의 핵심 주장은 AI 브라우저 에이전트의 프롬프트 인젝션 취약점은 실제 브라우저 환경에서 동적으로 테스트해야 한다는 것이다.

브라우저 에이전트는 웹페이지 전체를 읽고, 요약하고, 사용자의 권한으로 여러 작업을 수행할 수 있다.  
따라서 웹페이지 안에 숨겨진 악성 명령은 기존 웹 보안 경계를 우회할 수 있다.  
정적 템플릿 기반 테스트만으로는 실제 공격 가능성을 충분히 확인하기 어렵다.  
LLM을 이용해 공격 payload를 반복적으로 변형하면 기존 방어를 우회하는 더 정교한 간접 프롬프트 인젝션을 찾을 수 있다.  
특히 페이지 요약과 질의응답 기능은 페이지 내용을 광범위하게 읽기 때문에 공격 위험이 높다. 논문은 페이지 요약 기능과 질문응답 기능에서 각각 높은 공격 성공률을 보고한다.

### 의의

이 논문의 의의는 LLM 보안 테스트를 실제 브라우저 환경으로 가져왔다는 점에 있다. 기존의 프롬프트 인젝션 연구는 주로 텍스트 입력과 모델 응답을 중심으로 분석하는 경우가 많았다. 그러나 AI 브라우저 에이전트는 실제 웹페이지, DOM, 사용자 세션, 브라우저 권한, 확장 기능과 연결된다.

따라서 브라우저 에이전트의 보안성은 단순히 모델이 악성 프롬프트를 거절하는지 확인하는 방식으로는 충분히 평가할 수 없다. 실제 웹페이지 안에 숨어 있는 지시를 모델이 어떻게 해석하는지, 그 결과 어떤 브라우저 행동을 실행하는지까지 테스트해야 한다.

이 논문은 LLM 기반 브라우저가 보편화될수록 보안 테스트 방식도 정적 분석에서 동적 fuzzing으로 확장되어야 함을 보여준다. 특히 공격자가 LLM을 사용해 공격 문구를 자동 변형할 수 있다는 점은 방어자도 지속적인 자동 테스트 체계를 갖추어야 한다는 의미를 가진다.

### 느낀점

이 논문은 AI 브라우저가 편리한 자동화 도구인 동시에 매우 위험한 공격 표면이 될 수 있음을 보여준다. 브라우저는 사용자의 로그인 세션, 개인정보, 업무 페이지, 이메일, 클라우드 서비스에 접근할 수 있다. 여기에 LLM 에이전트가 결합되면, 웹페이지 속 숨겨진 명령이 사용자의 권한으로 실행될 가능성이 생긴다.

중요한 점은 사용자가 직접 악성 명령을 입력하지 않아도 공격이 발생할 수 있다는 것이다. 사용자는 평범한 웹페이지를 열었을 뿐이지만, AI 에이전트는 그 페이지 안의 숨겨진 지시를 읽고 잘못된 행동을 할 수 있다. 따라서 AI 브라우저 보안에서는 페이지 콘텐츠를 신뢰할 수 없는 입력으로 보고, 에이전트의 행동 권한을 제한해야 한다.

이 논문은 LLM 기반 브라우저를 실제 서비스로 운영하려면 프롬프트 필터링보다 더 강한 구조적 통제가 필요하다는 점을 보여준다. 브라우저 에이전트는 민감한 작업을 자동 실행하기 전에 사용자 승인, 출처 검증, 도메인 격리, 권한 제한, 행동 로그 검증을 거쳐야 한다.

## 의도 기반 분류의 장점과 한계

공격을 “어디를 공격했는가”가 아니라 **무엇을 노렸는가**로 나누는 방식이다.

예를 들면 다음과 같다.

|분류|의미|
|---|---|
|데이터 대상 공격|개인정보나 중요한 데이터를 훔치거나 바꿈|
|모델 대상 공격|모델이 잘못 판단하게 만듦|
|MAS 대상 공격|여러 에이전트가 협력하는 시스템 전체를 망가뜨림|

이 방식의 장점은 **공격 목적이 잘 보인다**는 것이다.  
하지만 한 공격이 여러 목적을 동시에 가질 수 있어서 분류가 애매할 수 있다.

예를 들어 악성 문서를 읽은 에이전트가 잘못 판단하고, 도구를 실행해 데이터를 유출한다면 데이터 공격이기도 하고 모델 공격이기도 하다.

## 두 분류 모두에서 어려운 사례

분류가 어려운 사례는 **복합적·연쇄적 공격**이다. 예를 들어 공격자가 문서 안에 숨겨진 프롬프트를 삽입하고, 에이전트가 이를 읽은 뒤 잘못된 계획을 세우며, 외부 도구를 호출해 데이터를 유출하고, 그 결과를 다른 에이전트에게 전달한다고 가정할 수 있다.

이 공격은 구성 요소 기준으로 보면 perception, brain, tool, memory, communication을 모두 거친다. 의도 기준으로 보면 데이터 탈취, 모델 판단 왜곡, 다중 에이전트 시스템 교란이 모두 포함된다. 따라서 이런 공격은 단일 분류에 넣기 어렵고, **다중 라벨 분류**나 **attack chain 기반 분류**가 더 적절하다.

결론적으로 의도 기반 분류는 공격의 목적과 피해를 이해하는 데 강하지만, 공격 경로의 기술적 세부 구조를 보여주는 데는 약하다. 구성 요소 기반 분류는 방어 지점을 찾는 데 유용하지만, 공격의 최종 목적을 설명하는 데는 부족하다. 따라서 두 방식은 대체 관계가 아니라 보완 관계로 보아야 한다.

# Question 3 답변 예시

## perception 방어 연구가 부족한 이유

논문이 perception-aspect defense를 중요한 연구 공백으로 지적한 것은 타당하다. LLM-based agent에서 perception module은 외부 환경을 읽고 해석하는 계층이다. 텍스트, 이미지, 웹페이지, 파일, API 응답, 센서 데이터, 브라우저 DOM 등 다양한 입력이 이 계층을 통해 agent 내부로 들어간다.

이 계층의 방어 연구가 부족한 이유는 세 가지로 볼 수 있다.

첫째, perception layer는 입력 형태가 매우 다양하다. Brain module은 주로 LLM의 추론과 의사결정을 다루고, memory module은 저장·검색·갱신 구조를 다룬다. 반면 perception layer는 텍스트뿐 아니라 이미지, HTML, PDF, 코드, 로그, 음성, 화면 정보 등 다양한 형식을 처리한다. 따라서 하나의 표준 방어 방법을 만들기 어렵다.

둘째, perception 공격은 정상 입력과 악성 입력의 경계가 모호하다. 예를 들어 웹페이지 안의 문장은 단순한 콘텐츠일 수도 있고, 에이전트에게 숨겨진 명령일 수도 있다. 사람에게는 보이지 않는 CSS-hidden text나 HTML comment 안의 명령도 모델에게는 입력으로 해석될 수 있다. 이런 경우 기존 필터링 방식만으로 악성 여부를 판단하기 어렵다.

셋째, 연구자들이 주로 brain module에 집중해 왔기 때문이다. LLM 보안 연구는 오랫동안 jailbreak, prompt injection, hallucination, alignment failure처럼 모델의 추론과 응답을 중심으로 발전했다. 상대적으로 perception layer는 모델 바깥의 전처리 문제나 입력 처리 문제로 간주되어 덜 주목받았다.

## brain·memory 방어와 다른 고유한 어려움

Perception layer 방어의 가장 큰 어려움은 **신뢰할 수 없는 외부 세계를 모델이 해석 가능한 입력으로 변환하는 과정 자체가 공격 표면**이라는 점이다.

**Brain module** 방어는 주로 모델이 잘못된 명령을 따르지 않도록 하는 데 집중한다. **Memory module** 방어는 저장된 정보가 오염되지 않도록 검증하고, 검색 시 악성 정보를 걸러내는 데 집중한다. 그러나 **perception layer** 방어는 그 이전 단계에서 “무엇을 입력으로 볼 것인가”, “어떤 정보가 명령이고 어떤 정보가 데이터인가”, “어떤 출처를 신뢰할 것인가”를 결정해야 한다.

예를 들어 AI 브라우저가 웹페이지를 요약할 때, 페이지의 본문 텍스트와 숨겨진 prompt injection 텍스트를 구분해야 한다. 단순히 텍스트를 모두 LLM에 전달하면 공격자가 페이지에 숨긴 명령이 agent의 의사결정에 영향을 줄 수 있다. 반대로 너무 강하게 필터링하면 정상적인 웹 콘텐츠 이해 능력이 떨어진다.

따라서 perception layer 방어는 입력 정제, 출처 검증, 형식별 파싱, hidden content 제거, multimodal consistency check, privilege separation이 함께 필요하다. 이는 단순히 모델을 더 안전하게 만드는 문제보다 훨씬 시스템적이고 복잡하다.

## 에이전트 기반 공격 능력 연구의 윤리적 문제

논문은 LLM-based agent가 공격 대상이면서 동시에 사이버보안에서 공격자 또는 방어자로 활용될 수 있다고 본다. 이는 중요한 이중성을 가진다. LLM agent는 취약점 분석, 침해 대응, 보안 로그 분석, 위협 탐지에 도움을 줄 수 있다. 반대로 공격 자동화, 피싱 생성, 취약점 탐색, 악성코드 작성, 사회공학 공격에도 사용될 수 있다. 논문도 Section 6에서 LLM-based agent가 사이버 공격과 방어 양쪽에 활용될 수 있음을 다룬다.

에이전트 기반 공격 능력을 연구하고 공개하는 것은 윤리적으로 복잡하다. 투명한 연구 공개는 방어자에게 위험을 이해하고 대응책을 만들 기회를 준다. 공격 가능성을 숨기면 실제 취약점이 존재해도 방어 체계가 발전하지 못한다. 특히 LLM agent처럼 빠르게 확산되는 기술에서는 공격 가능성을 공개적으로 분석하는 것이 필요하다.

하지만 지나치게 구체적인 공격 절차, 코드, 자동화 도구, 우회 프롬프트, exploit chain을 공개하면 악의적 행위자가 이를 바로 사용할 수 있다. 특히 LLM agent는 비전문가도 자연어로 공격 자동화를 수행할 수 있게 만들기 때문에, 공개 연구가 공격자의 진입 장벽을 낮출 위험이 있다.

## 투명성과 악용 위험의 균형

**Claude Mythos**

연구 커뮤니티는 완전한 비공개와 무제한 공개 사이에서 균형을 잡아야 한다. 적절한 방식은 다음과 같다.

첫째, 공격 원리와 위험성은 공개하되, 즉시 악용 가능한 세부 절차는 제한해야 한다. 예를 들어 공격 유형, 영향, 방어 필요성, 평가 결과는 설명할 수 있지만, 실제 서비스에 바로 적용 가능한 exploit script나 자동화 프레임워크는 제한적으로 공개해야 한다.

둘째, responsible disclosure가 필요하다. 특정 제품이나 서비스의 취약점을 발견한 경우, 논문 공개 전에 개발자나 운영자에게 수정 기회를 제공해야 한다.

셋째, 연구 결과는 방어 중심으로 구성되어야 한다. 공격 성공률만 강조하는 것이 아니라, 어떤 방어가 효과적이었고 어떤 조건에서 실패했는지 함께 제시해야 한다.

넷째, 고위험 기능은 통제된 환경에서만 공유해야 한다. 예를 들어 benchmark, red-team dataset, 공격 시뮬레이터는 인증된 연구자에게만 제공하거나, 실제 공격에 사용할 수 없도록 제한된 형태로 제공하는 방식이 필요하다.

결론적으로 에이전트 기반 공격 연구는 필요하지만, “할 수 있음을 증명하는 연구”에 그쳐서는 안 된다. 연구의 목표는 공격 능력 과시가 아니라 방어 설계와 위험 완화여야 한다.

## 보안과 유용성 사이의 긴장

논문에서 방어 평가 기준 중 하나로 Utility를 둔 것은 중요하다. Utility는 방어 기법이 적용된 뒤에도 LLM agent가 원래의 추론 능력과 작업 수행 능력을 얼마나 유지하는지를 의미한다. 논문은 공격과 방어 방법을 평가하기 위한 통합 기준을 제시하고, 방어 방법이 공격을 막는 성능뿐 아니라 agent의 정상 기능을 얼마나 보존하는지도 고려한다.

보안과 유용성 사이에는 어느 정도 근본적인 긴장이 존재한다. LLM-based agent는 외부 정보를 읽고, 추론하고, 도구를 호출하고, 여러 단계를 계획할수록 유용해진다. 그러나 바로 그 능력이 공격 표면을 넓힌다. agent가 더 많은 파일을 읽을 수 있고, 더 많은 API를 호출할 수 있으며, 더 자율적으로 행동할수록 공격자가 악용할 수 있는 지점도 많아진다.

예를 들어 강한 입력 필터링을 적용하면 악성 프롬프트를 줄일 수 있지만, 정상적인 복잡한 지시도 차단할 수 있다. 도구 호출을 엄격히 제한하면 위험한 실행은 줄어들지만, agent의 자동화 능력도 떨어진다. 모든 민감 작업에 인간 승인을 요구하면 보안성은 높아지지만 실시간성과 편의성은 감소한다.

따라서 보안과 유용성 사이의 긴장은 완전히 사라지기 어렵다.

## 현재 방법론의 한계도 존재함

그러나 이 긴장이 전적으로 근본적인 것은 아니다. 현재 방어 방법이 아직 정교하지 못하기 때문에 생기는 손실도 크다. 많은 방어 기법은 입력을 단순히 차단하거나, 모델 응답을 후처리하거나, rule-based guardrail을 추가하는 방식이다. 이런 방식은 공격과 정상 입력을 세밀하게 구분하지 못하기 때문에 utility를 낮춘다.

즉, 현재의 medium utility는 “보안과 유용성은 원래 양립 불가능하다”는 증거라기보다, 현재 방어 구조가 아직 거칠고 맥락 이해 능력이 부족하다는 증거로 해석할 수 있다.

## 미래 아키텍처의 해결 방향

미래의 LLM agent 아키텍처는 보안과 유용성의 충돌을 줄이기 위해 더 세분화된 구조를 가져야 한다.

첫째, 명령과 데이터를 명확히 분리해야 한다. 외부 문서, 웹페이지, 이메일, API 응답은 기본적으로 명령이 아니라 데이터로 처리되어야 한다. 모델이 외부 콘텐츠 속 명령을 직접 따르지 않도록 architecture-level separation이 필요하다.

둘째, 권한 기반 실행 구조가 필요하다. agent가 모든 도구를 항상 사용할 수 있게 하는 대신, 작업 맥락과 위험도에 따라 최소 권한만 부여해야 한다.

셋째, perception, brain, memory, action module 사이에 검증 계층을 두어야 한다. 예를 들어 perception layer는 입력 출처와 숨겨진 콘텐츠를 검증하고, brain module은 계획의 안전성을 점검하며, action module은 실행 전 정책 위반 여부를 확인해야 한다.

넷째, 위험도 기반 adaptive defense가 필요하다. 모든 입력에 동일한 강도의 방어를 적용하면 utility가 떨어진다. 낮은 위험 작업은 빠르게 처리하고, 민감한 데이터 접근이나 외부 전송 같은 고위험 작업에만 강한 검증을 적용해야 한다.
